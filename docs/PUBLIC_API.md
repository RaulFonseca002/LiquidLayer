# Solid v0.1 Public API

Status: approved contract for version 0.1.0.

Solid is a private, reusable C++20 framework. Installed consumers use `find_package(Liquid 0.1 CONFIG REQUIRED COMPONENTS Core)`; source consumers may use `add_subdirectory`. The exported static targets are `Liquid::Core`, `Liquid::Lua`, and `Liquid::Simulation`.

All public symbols are in `liquid::` or a child namespace. Public headers expose values, world-bound generational handles, `World`, `Runtime`, systems, codecs, effects, adapters, event stores, replay, and simulation APIs. Registries, `Coordinator`, `WorldState`, component storage, raw slots, and implementation helpers are not public API. Template implementation dependencies are installed under `liquid/detail`; consumers must not include those headers directly, and their names and layout may change without compatibility notice.

A public handle contains a world identity, slot, and 32-bit generation. Stale and cross-world handles are rejected. Exhausted generations retire their slots. `SessionId`, `CommandId`, and `RecordId` are monotonic, non-recyclable identifiers within their documented scope.

Component registration requires a stable schema name and version plus a `ComponentCodec<T>`. Optional effect production requires a bidirectional `EffectCodec<T>` and stable adapter route: selected encoded values become commands, while authoritative device values decode back into the component. Component reads are const borrows invalidated by structural mutation. Mutation uses transactional `update_component` or `replace_component`; validation and encoding succeed before state and journal records commit.

Systems register in the `Input`, `Behavior`, or `Decision` phase. A frame applies queued feedback before running Input systems, then runs Behavior and Decision systems, resolves every live intent target, derives effects, dispatches, and records completion. `ComponentControl` declares whether a selected intent is evidence only, commits internal state, or drives a bound external effect. External components change only after authoritative reports or revisioned observations.

`Liquid::Lua` provides `LuaBehaviorScript`, `LuaLifecycleSystem`, and `LuaBehaviorRunner`. Lifecycle scripts execute in one fresh sandbox per behavior per frame and may define `on_start(frame)`, `on_components_changed(frame, changes)`, and `on_frame(frame)`. Proposals, cancellations, and watch registrations commit as one successful callback bundle; a callback failure commits none of them. Script state lives in ordinary codec-backed components, never in a retained Lua VM.

Liquid L0 (unreleased; awaiting review) adds described Lua bindings to `Liquid::Lua`, with no new target. `liquid/scripting/LuaValueSchema.hpp` provides the immutable `LuaValueSchema` (Boolean, Integer, Number, String, Array, Object factories that throw `std::invalid_argument` on invalid or over-limit trees), `LuaSchemaField`, `LuaModelBindingMetadata` (read schema, write schema, description) with `symmetric_metadata`, and `validate_lua_value`, which returns the first `LuaSchemaError` (`Kind`, `Range`, `MissingField`, `UnknownField`, `Limit`) with a Lua-style path. `LuaBehaviorRunner::expose_component` gains a four-argument overload taking metadata: registration rejects metadata whose worst case exceeds the runner limits, proposals failing the write schema are `InvalidProposal`, and snapshots failing the read schema are `HostError`. The three-argument overload is unchanged. `liquid/scripting/LuaCapabilityManifest.hpp` provides `LuaBehaviorRunner::capability_manifest(world, behavior, now)`, which returns a `LuaManifestResult`: either an immutable, copied `LuaCapabilityManifest` (authoring contract `liquid.lua.authoring/1`, `now_ms`, limits, authoring notes, and capabilities sorted by script type and component name, each with mode, Lua access expression, schemas and read value), or a `LuaManifestError` (`InvalidBehavior`, `SnapshotUnavailable`, `SchemaMismatch`, `LimitExceeded`, `HostError`). The first successful capture freezes binding registration. A manifest describes capabilities; it grants no execution permission. Callers of `capability_manifest` include `LuaCapabilityManifest.hpp`.

Liquid L1 (unreleased; owner-approved) adds the opt-in `Liquid::Authoring` component (built with `LIQUID_BUILD_AUTHORING=ON`, requested with `COMPONENTS Authoring`; it depends on `Liquid::Simulation`). `Liquid::Lua` gains `LuaScopeGrant` (script type name, component name, `ComponentAccessMode`), the host-only `LuaBehaviorRunner::scope_manifest(world, grants, now)`, which captures a prospective manifest from trusted grants without creating a behavior and does not read Write-only grants, `LuaManifestCaptureKind` (`Behavior`, `ProspectiveScope`, exposed by `LuaManifestCapture::kind()`), and the additive `LuaManifestErrorCode::InvalidGrant` for empty, duplicate, unnamed, unknown, undescribed or missing grant targets. Three further additive Lua APIs support the session: `LuaCapabilityManifest::logical_bytes()` returns the L0 logical size of a built manifest, which the session checks against `maxManifestBytes`; `LuaScopeTarget` is one resolved target identity (component type and slot, no value); and the host-only `LuaBehaviorRunner::scope_targets(world, grants)` resolves those identities in grant order without reading values, never encodes and does not freeze registration. `liquid/authoring/Types.hpp` provides `AuthoringResult<T>` (exactly one value or one `AuthoringError`, with `AuthoringResult<void>` for empty success), `AuthoringError` (`AuthoringErrorCode`, a diagnostic bounded with its field path to `AuthoringMaxDiagnosticBytes`, optional `fieldPath`), `AuthoringSessionId` (created only by `from_hex` from 32 lowercase hexadecimal digits), the nonzero typed `ScopeId`, `ProposalId` and reserved `ManagedBehaviorId`, `CallerContext` (session and owner), `AuthoringLimits` (contract defaults a host may lower but not raise), and `ScopeGrant`, an alias of `LuaScopeGrant`. `liquid/authoring/AuthoringSession.hpp` provides `AuthoringSession`, constructed from an `AuthoringSessionId`, `Runtime&`, `LuaBehaviorRunner&`, the World's `ComponentType<LuaBehaviorScript>` and `AuthoringLimits`; the constructor throws `std::invalid_argument` for a foreign or invalid script type or invalid limits, and every other call returns an `AuthoringResult`. Trusted-host `create_scope` and `replace_scope` (complete replacement; the revision always increments) return a `ScopeView` (scope, revision, copied `LuaCapabilityManifest`), and `revoke_scope` returns `AuthoringResult<void>` (the scope is erased, so later calls return `NotFound`); script-control components are never exposed. Caller-checked `discover` re-resolves every target and returns fresh copies, `submit` admits a `ProposalSubmission` as an immutable `BehaviorProposal` without executing Lua or changing World, and `proposal` returns a copy of that record. A removed or recreated target is `StaleScope`; unknown or foreign-caller IDs are `NotFound`. L1 claims no syntax checking, evaluation, approval or activation.

Adapters are registered with `std::shared_ptr<EffectAdapter>` so their lifetime covers every outstanding command and retry. An externally supplied `EventStore*` is a non-owning host service and must outlive the `Runtime`.

The framework makes no stable binary ABI promise before 1.0. Source compatibility follows [SUPPORT.md § Compatibility](SUPPORT.md#compatibility).

## Threading

*(formerly `docs/THREADING.md`, "Threading and Ownership Contract"; text verbatim)*

`World`, `Runtime`, systems, adapters during synchronous dispatch, and writable event stores are confined to the creating thread. Public entry points reject use from another thread before mutation. Hosts provide any broader synchronization.

`FeedbackSender` is the deliberate cross-thread boundary. It is thread-safe, bounded, and accepts immutable `EffectReport` values from concurrent producers. Queue overflow is reported to the producer and never silently drops a report. Shutdown prevents new sends, wakes waiters, and permits deterministic draining or discard according to the selected close operation. Destroying `Runtime` invalidates its senders safely.

Runtime snapshots the queued reports at the beginning of a frame. Reports arriving after that snapshot wait for the next frame. Immediate feedback is limited to a report returned synchronously by the dispatch call; asynchronous reports always use the queue.
